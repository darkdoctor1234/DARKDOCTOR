# Darkdoctor (DD-V2) — Project Handover

Give this whole file to a new Claude session as your first message (e.g. "Read HANDOVER.md in this project and get up to speed") so it doesn't have to rediscover everything from scratch.

## What this is

Darkdoctor is a review platform for Indian medical colleges (MBBS/Dental/Nursing, UG+PG) — students and alumni review colleges, ask questions, and discuss. Direct competitor: MedReview (medreview.medicaldrafts.com), NEET-PG/INI-CET focused.

**Stack**: Django 5 + DRF + SimpleJWT + PostgreSQL (`backend/`) · Next.js 16 App Router, React 19, Turbopack, PWA (`frontend/`). All frontend styling is inline `style={}` — no CSS framework or component library. Theming via CSS vars + `data-theme` attribute.

## Structure

- `backend/modules/`: `accounts` (User + UserProfile, admin CRUD, leads — see `constants.py` for the PG-department taxonomy), `authentication` (per-role JWT login, OTP password reset, permission classes), `colleges` (College/Department/Seat-Fee-Stipend entries, Review, Question/Answer, bulk Excel import), `about` (singleton content), `communities` (Specialty Communities v2 — Community/CommunityMembership/DiscussionPost/PollOption/PollVote/CommunityComment + report models; **rebuilt from scratch a second time**, see "Specialty Communities v2" below — the app label is unchanged but the data model is not the same as either earlier version).
- Three roles: `user`, `admin`, `super_admin` (`accounts.User.Role`).
- `frontend/app/`: public pages (feed/colleges/communities/profile/login/signup/about) under a shared `UserShell`; `/admin` (role=admin — was a do-nothing dashboard, now does real work: review approvals, see "Review Approval Workflow" below); `/superadmin/*` (home, admins, colleges add/bulk-import, leads, review moderation, communities moderation, about editor — role=super_admin, each route gated by its own `layout.tsx`).
- `frontend/lib/*Api.ts`: one client module per domain (`api.ts` = auth, `collegeApi.ts`, `profileApi.ts`, `questionsApi.ts`, `adminApi.ts`, `leadsApi.ts`, `aboutApi.ts`, `communitiesApi.ts`). Session lives in `sessionStorage` (`lib/auth.ts`) — **no silent token refresh**, a 401 just clears session and redirects to `/`.

## Specialty Communities v2 — built (read this before touching Community/membership code)

Real spec from the client (relayed by the user): Community is **membership-based and PG-only**, modeled on WhatsApp groups / Reddit, not an open forum. Every PG-eligible user belongs to **exactly the same three communities**, auto-derived from their profile — never a browsable directory of every community that exists:

1. **National Overall** — every PG-eligible user, one singleton community.
2. **Department–National** — everyone in their PG specialty, nationwide.
3. **Department–State** — everyone in their PG specialty **and** their PG college's state.

Built end-to-end and verified live end-to-end with two real test accounts (auto-membership on profile save, posting, poll voting, commenting, reporting, and the super-admin approve/remove flow, all through the actual UI — not just API calls).

- **Eligibility** — `UserProfile.COMMUNITY_ELIGIBLE_STATUSES` = `{pg_student, working_professional, alumni, faculty}` (never UG; `pg_aspirant`/`other` also excluded). **"Faculty / Professor" is a brand-new profile status** added specifically for this — it didn't exist anywhere in the app before ("prof" in the client's spec turned out to mean actual teaching faculty at an institution, not just working doctors). It shows up in `STATUS_OPTIONS` everywhere status is picked (signup, profile, feed's journey picker) — if you're hunting for why there are now 8 statuses instead of 7, this is why.
- **PG specialty is a new required-for-communities profile field** — `UserProfile.pg_department`, a fixed-choice `CharField` (not free text, deliberately — free text would fragment doctors in the same specialty across near-duplicate groups). The choice list lives in `backend/modules/accounts/constants.py` (`PG_DEPARTMENT_CHOICES`) and **must stay in sync with** `frontend/lib/departments.ts` (`ALL_DEPARTMENTS`) — the same ~35-department taxonomy already used for Review's department tagging, reused here rather than inventing a third list. Collected on the profile page and at signup step 2 (both gated behind `showPg`, right after the PG-college picker).
- **State** = the state of the user's `pg_college` (not a separate home-state field — there isn't one, and the client confirmed college state is what they meant).
- **Auto-membership, "soft leave" model** (`modules/communities/services.py:sync_memberships`, called from `ProfileMeView.post/patch` in accounts and from `RegisterSerializer.create` in authentication — both best-effort, wrapped in try/except so a sync failure never blocks a profile save or registration): the moment a profile becomes eligible, it's auto-added to all applicable communities. `CommunityMembership.is_active=False` on Exit is a **soft leave** — the row is never deleted, so a later profile save can never silently re-add something the user deliberately left. Join either flips `is_active` back on or creates a new row (e.g. after changing specialty). Department–State `Community` rows are created **lazily** (`get_or_create`) the first time someone needs one, not pre-seeded for all ~35 departments × ~30 states.
- **Identity is real, not anonymous** — explicit, deliberate reversal of the Review/Q&A/v1-Communities anonymity principle, per the client: "anonymous in reviews, names can be visible in community." `display_name` = `full_name` (falls back to username, then "Doctor"), plus an `author_department` badge. Don't accidentally carry the anonymity pattern over here from Review-adjacent code — it's wrong for this feature specifically.
- **Everything is membership-gated, both reads and writes** — unlike v1 (and unlike Review/Q&A), you cannot even *read* a community's posts/comments without an active membership; the backend checks this on every relevant endpoint (`_active_membership` in `communities/views.py`), not just the frontend. A community you're not in simply 403s.
- **Member count only, no member list/directory** — explicit client answer ("only number of people in the group should be visible, no names of doctors needed"). Don't build a "who's in this group" browsing UI without checking with the user first — it was specifically declined.
- **No DMs** — explicit client answer ("only group and everyone sees"). Everything posted is visible to the whole community, nothing private.
- **Unread badge, not a notification system** — a small dot on the Communities nav tab (`UserShell.tsx`) when any community has activity since the user's `last_seen_at` for it (`Community.last_activity_at`, denormalized and bumped on every new post/comment, compared against `CommunityMembership.last_seen_at`, bumped when the user opens that community's feed). Explicit client answer: "just like new msgs icon like we have in instagram" — a presence indicator, not push/email notifications. Don't build real notification infrastructure without being asked.
- **Moderation** — report + super-admin approve/remove, same pattern as `Review`: `DiscussionPostReport`/`CommunityCommentReport`, auto-flag at 5 reports (`AUTO_HIDE_THRESHOLD` in `communities/services.py`), a super-admin queue at `/superadmin/communities` (new `ModuleCard` on `/superadmin/home`) covering both posts and comments in one page with a tab switch. This is the **platform's one admin system**, not a per-group elected "group admin" — confirmed with the client rather than assumed.
- **API**: `GET /communities/mine/` (all — active or exited — of the user's ≤3 communities, never a full directory), `POST /communities/{id}/join/` and `/exit/`, `GET/POST /communities/posts/?community={id}`, `GET /communities/posts/{id}/`, `POST /communities/posts/{id}/vote/`, `GET/POST /communities/posts/{id}/comments/`, `POST .../report/` on both posts and comments, `GET /communities/posts/flagged/` + `/comments/flagged/` and `PATCH .../{id}/admin/` (super-admin only).
- **Frontend routes**: `/communities` (your ≤3 communities, Join/Exit buttons) → `/communities/[communityId]` (that community's feed + New Post) → `/communities/[communityId]/posts/[postId]` (full post, poll voting, comments, report). Note the route shape changed from v1's flat `/communities/[id]` (which was a post, not a community) — old links/bookmarks to that shape are gone.
- **Not built / left for later, don't assume it exists**: per-community moderators (explicitly declined — see above); a member directory (explicitly declined); DMs (explicitly declined); real push/email notifications (explicitly declined, badge only); any UI for admin-managing the fixed department taxonomy beyond django-admin.

## College Directory enhancements (a later session again)

A friend of the user's shared a spec for a *different* app's ("DarkDoctor" React/Vite, different data model — BDS/BSc course names, blue/purple Govt/Private theming) College Directory. The user said to take only what's relevant, not copy it — three ideas were confirmed via `AskUserQuestion` and built; two were explicitly declined and are documented here so they aren't second-guessed later:

- **Built — default to own college** (`app/colleges/page.tsx`): a signed-in user whose profile has a `ug_college`/`pg_college` visiting `/colleges` is redirected (`router.replace`) straight to that college's detail page instead of the full list — prefers `pg_college` over `ug_college` if both are set. `?all=1` always skips this and shows the list; the detail page's "← Colleges" breadcrumb, its error-state "Back to Colleges" button, and the delete-college redirect all link to `/colleges?all=1` for exactly this reason — don't repoint them at bare `/colleges`, that would just bounce the user back to their own college. The main "Colleges" nav tab in `UserShell` intentionally stays as bare `/colleges` — landing on your own college is the whole point of clicking it.
  - **Watch out**: the loading-state boolean for this (`checkingDefault`) must never be computed by calling `isAuthenticated()` synchronously in `useState()`'s initializer — that runs during SSR too (where there's no `sessionStorage`) and produces a different result than the client's first render, which breaks hydration app-wide (a real bug hit and fixed this session — showed up as a React "Hydration failed" console error). It has to start at a server-safe default (`false`) and only flip inside a `useEffect`.
- **Built — star rating on list cards** (`CollegeCard.tsx` + `collegeApi.ts` + backend): `CollegeListSerializer`/`_COLLEGE_LIST_QUERYSET` in `colleges/views.py` now annotate each college with `avg_rating` (Django `Avg` over visible reviews' `rating_overall` field only, as a cheap stand-in for the 5-category average — not the same computation as `Review.average_rating`) and `review_count`. Cards show a star + the number when `avg_rating` isn't null; colleges with zero reviews show no rating (no fake/placeholder score).
- **Declined — do not silently reintroduce**: (1) emoji badges/blue-purple theming for Govt/Private — kept the existing SVG-icon, teal/violet convention instead (also consistent with the emoji-aversion note above); (2) reorganizing the detail page's Reviews/Q&A/Discussions into horizontal tabs like the Profile page — explicitly declined, sections stay stacked as they were.

## Review Approval Workflow (a later session again)

The client's second real spec this stretch: reviews should no longer post immediately — an admin must approve or reject each one before it's ever visible, and the (previously dormant) `admin` role is who does this day-to-day, not `super_admin`. Confirmed answers before building: rejection requires a reason, and the review's own author can then edit and resubmit the *same* review rather than starting over; Q&A/Discussions are explicitly untouched (no approval gate — the client was clear this is reviews-only); reported (already-live, 5+ report) reviews are handled by the same `admin` role too; super admin keeps a superset view with an audit trail of who resolved what and full override power.

- **`Review.status`** gained two new values on top of the existing `visible`/`flagged`/`removed`: **`pending`** (the new default for every new review — invisible until acted on) and **`rejected`** (author can edit-and-resubmit). Also new: `rejection_reason` (text) and `resolved_by` (FK to the acting admin/super-admin, for the audit trail) — all in `modules/colleges/models.py`, migration `0008_review_rejection_reason_review_resolved_by_and_more`.
- **One row per college per user, reused across the whole lifecycle** — a rejected review isn't deleted and resubmitted as a new row; `PATCH /colleges/reviews/{id}/resubmit/` (`ReviewResubmitView`, author-only, only while `status=rejected`) edits the same row in place and flips it back to `pending`, clearing the reason and resolver. ## Review-farming loophole closed: locked college fields + change requests (same session, right after Notifications)

The user spotted a real exploit: reviews are gated to "colleges you're affiliated with" (`profile.ug_college`/`pg_college`), but Settings let you freely change your college at any time — so anyone could set their college to A, post a review, change to B, post again, and so on indefinitely, since the affiliation check only ever looks at your *current* profile value. The user's own proposed fix, confirmed before building: **lock a college field after it's first set**; changing it afterward needs a proof document, reviewed by an admin (mirrors the existing review-approval pattern). A UG student who starts PG elsewhere just *adds* a PG college — that's a first-time set, not a change, so it stays free. ## Neon migration — local Postgres → managed Neon Postgres (same session, 2026-09-16)

The client created a Neon project (org "DARK DOCTOR", project "DARKDOCTOR", region **AWS Asia Pacific 1 / Singapore** — chosen deliberately over the default Ohio region after checking live that Neon has no Mumbai region, Singapore is the closest available) and asked for a full schema + data migration, explicitly emphasized to be careful, verified, and gap-free. Backend now points at Neon permanently — local Postgres (`darkdoctor` on `localhost`) still exists untouched as a fallback, just no longer the active config.

**Method** (deliberately not a raw `pg_dump`/restore of everything in one shot):
1. `pg_dump` the local DB in full (schema+data, custom format) to a scratchpad file first — the actual safety net for the whole operation, verified restorable (`pg_restore --list`) before touching anything else.
2. Schema built on Neon via `manage.py migrate` against Neon's **direct** (non-pooled) connection — not copied via SQL — so it's byte-identical to what's already tested locally, no risk of DDL/version drift between local Postgres 18.1 and Neon's 18.6.
3. Data copied via `pg_restore --data-only --single-transaction` from the local dump into Neon (direct connection), **explicitly excluding** `django_migrations`, `django_content_type`, `auth_permission` — those three are auto-populated by Django's own migration/post-migrate machinery and were already correctly (and more cleanly — see below) populated by step 2; force-restoring local's copies on top would have risked unique-constraint conflicts for zero real benefit, since no app model has an FK into any of them.
4. **A real, serious bug caught and fixed**: `pg_restore --data-only` inserts explicit primary-key values but never advances the sequence (auto-increment) counters that generate *new* ones. Left alone, every sequence sat at `1` while real data went up to id 1646/30451/etc — the very next INSERT into any table would have collided with existing data and failed (or worse, in an edge case). Fixed generically for all 37 sequences in the schema via `pg_get_serial_sequence()` (not a hand-written table list, and not `pg_depend` — see below), each set to `max(id)` via `setval(..., true)`.
5. SSL enforced end-to-end: `DB_SSLMODE=require` and `DB_CHANNEL_BINDING=require` added as new conditional `OPTIONS` in `config/settings/base.py`'s `DATABASES` (only applied when set — local dev, which needs neither, is unaffected), matching Neon's own connection string exactly. Channel binding is extra SCRAM-auth protection against credential replay even over TLS, and Neon includes it by default — honored it rather than dropping it for simplicity.

**Two real technical snags hit and resolved, worth knowing before touching this again:**
- **`pg_restore --disable-triggers` fails on Neon** with `permission denied: ... is a system trigger` — Neon's managed service doesn't grant even the database owner role enough privilege to disable RI (foreign-key) system triggers, only true superuser can. Not needed anyway: `pg_restore`'s custom-format archive already encodes correct dependency order in its TOC, so a straight data-only restore without `--disable-triggers` succeeded cleanly once all parent+child tables were included together in the same `-t` list. `--single-transaction` is what made the first failed attempt safe — confirmed a full atomic rollback (zero rows anywhere) before retrying differently, so nothing was ever left in a partial state.
- **My first sequence-fix script (`pg_depend`-based, looking for `deptype = 'a'`) silently found nothing and fixed nothing** — Django 5 generates Postgres `GENERATED BY DEFAULT AS IDENTITY` columns, not old-style `SERIAL`, and identity-column sequences use a different `pg_depend` dependency type than what that query checked for. Switched to `pg_get_serial_sequence()`, the correct version-and-mechanism-agnostic way to resolve a column's sequence regardless of how it was created — confirmed working via `RAISE NOTICE` output listing all 37 sequences found and corrected.

**Verification, not just assumption** — three independent checks, not one:
- Row counts compared table-by-table between local and Neon (`information_schema.tables` + `query_to_xml` for a generic per-table count query) — every real-data table matched exactly; only the three deliberately-excluded tables differed, and Neon's versions were *more* correct (one fewer stale content-type row than local, left over from a since-removed model earlier in this project's history).
- `md5(string_agg(name, ',' ORDER BY id))` over all 823 `colleges_college` rows — identical hash on both sides, strong evidence the actual data (not just row counts) is byte-identical.
- A real Django-ORM write test (not raw SQL) — created a throwaway `College` row via `manage.py shell` after the sequence fix, got `id=1647` (correctly continuing right after the existing max of 1646, no collision), deleted it. This is what actually proves the sequence fix works through the application, not just in isolation.
- Full app-level smoke test after pointing `.env` permanently at Neon: fresh `manage.py runserver`, real HTTP calls — `GET /api/v1/colleges/` returns all 823, and a real login (`tarun@gmail.com`) succeeds with `email_verified: true` intact.

**A process-hygiene trap hit again during this work, same class as earlier in this session**: while testing, a batch of orphaned `runserver` processes from earlier in this long session (started both by me and by the client following manual-run instructions I'd given) meant `curl`-ing port 8000 was briefly answered by a *stale process still on the old local-Postgres config*, right after a *new* process had just crashed on a transient Neon DNS hiccup — momentarily looking like Neon was working when it wasn't actually being tested at all. Caught by checking which PID actually owned port 8000 (`Get-NetTCPConnection`) rather than trusting a successful-looking `curl` response at face value. **Lesson reinforced**: in a long session, always confirm which process is actually answering a port before trusting a test result — don't assume the most recently started command is the one responding.

**`.env` now**: `DB_HOST` is Neon's **pooled** endpoint (`...-pooler...`, correct for the multi-worker gunicorn production setup), `DB_USER=neondb_owner`, `DB_NAME=neondb`, plus the new `DB_SSLMODE`/`DB_CHANNEL_BINDING`. The direct (non-pooled) endpoint was only ever used for the one-time migration commands, never written to `.env`. Old local values are preserved in a comment, not deleted — reverting to local Postgres is a one-line `.env` edit away if ever needed, and local Postgres itself still has every row it always did.

## Supabase migration — local media disk → Supabase Storage (same session, 2026-09-16)

Same "no gaps, no threats" bar as the Neon migration, applied to media files. The client created a Supabase project (region **South Asia / Mumbai, ap-south-1** — deliberately available here, unlike Neon which had no Mumbai option) and a public Storage bucket `darkdoctor-media` (10MB size limit, no MIME restriction — left open deliberately since some of the 5 real files are `.txt` test files that a MIME allowlist would have blocked). Only Supabase **Storage** is used — its separate Postgres offering is not used; Neon remains the database.

**Inventory first**: `backend/media/` had exactly 5 real files (`college_change_proofs/4/{admission_letter.txt, bonafide_certificate.txt, proof_test.txt, proof_test_V3uWmsJ.txt}`, `reviews/1646/prof_pic.jpeg`), cross-checked 1:1 against `colleges_reviewimage.image` / `accounts_collegechangerequest.proof` rows in Neon — no orphans in either direction before starting.

**Method**:
1. Connectivity tested in isolation first via `boto3` against Supabase's S3-compatible endpoint (`https://<project-ref>.storage.supabase.co/storage/v1/s3`, path-style addressing, `s3v4` signatures, separate access-key/secret pair generated in Supabase's S3 Configuration panel — distinct from its Postgres credentials) before touching real files.
2. All 5 files uploaded preserving their exact relative path/key (Django's `FileField` only ever stores the relative path in the DB, never a full URL — so the storage backend can change with zero DB writes, as long as keys match exactly).
3. Integrity verified via MD5-vs-ETag comparison per file (Supabase's `ETag` on a plain, non-multipart `PutObject` equals the object's MD5 hex digest) plus size comparison — all 5 matched exactly. Confirmed again via a final `list_objects_v2` showing precisely 5 objects, correct keys and sizes, nothing extra.
4. Django wired to Supabase: `config/settings/base.py`'s existing S3 `STORAGES` block (originally written assuming native AWS) extended with `AWS_S3_ENDPOINT_URL` (the S3-protocol endpoint, used for all read/write/list operations) and `AWS_S3_ADDRESSING_STYLE = "path"` (auto-set whenever `AWS_S3_ENDPOINT_URL` is set). `AWS_S3_CUSTOM_DOMAIN` — the separate domain Django builds *public* file URLs from — was corrected to Supabase's actual public-serving pattern (`<project-ref>.supabase.co/storage/v1/object/public/<bucket>`), which is a **different host** from the S3 API endpoint. Both are env-driven (`.env`, `.env.example`), and the whole block stays inert (falls back to local disk) unless `AWS_STORAGE_BUCKET_NAME` is set — unrelated to the Supabase-specific settings, so real AWS S3 still works unchanged by just leaving `AWS_S3_ENDPOINT_URL`/`AWS_S3_CUSTOM_DOMAIN` blank.

**A real thing investigated and ruled a non-issue**: after wiring, a live write test (`default_storage.save()` via Django ORM) showed `default_storage.exists()` returning `False` immediately after a successful save, even though the file was confirmed present and correctly served via direct HTTP GET. Traced to `django-storages`' own source (`storages/backends/s3.py`, `S3Storage.exists()`): `if self.file_overwrite: return False` — a deliberate short-circuit, not a bug, active because `AWS_S3_FILE_OVERWRITE` defaults to `True` (uploads to the same key overwrite rather than get a random-suffix rename). Pre-existing `django-storages` behavior, unrelated to and unaffected by the Supabase switch — would behave identically on real AWS S3.

**Verification, matching the Neon methodology**:
- All 5 real files pulled through the **live running Django app** (not just the bucket directly) — `default_storage.url()` on each of the 5 real `ReviewImage`/`CollegeChangeRequest` rows produced the correct Supabase public URL, and a direct `curl` to every one of those 5 URLs returned `200` with the exact original byte size.
- A real write+read+delete test through the Django ORM/storage API (not raw `boto3`): created a throwaway file via `default_storage.save()`, read its content back (byte-identical), confirmed via raw `list_objects_v2` it existed with the right key/size, deleted it, and re-listed the bucket to confirm it's back to exactly the original 5 objects — nothing left behind.
- Process hygiene re-applied from the Neon lesson: killed 4 stale `runserver` processes (started before the `.env`/settings edits) before the live test, so the test was verifiably exercising the new config, not a leftover process still running old settings.

**`.env` now** (in addition to the Neon `DB_*` vars): `AWS_STORAGE_BUCKET_NAME=darkdoctor-media`, real `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, `AWS_S3_REGION_NAME=ap-south-1`, `AWS_S3_ENDPOINT_URL` (S3 API host), `AWS_S3_CUSTOM_DOMAIN` (public-serving host) — the two hosts are genuinely different domains, don't conflate them when touching this again. Local `backend/media/` disk copies were never deleted — they're just no longer read from, since the app now reads/writes exclusively through Supabase.

**Still open**: `backend/deploy/AWS_SETUP.md` and the two AWS IAM/bucket-policy JSON files still describe the original all-AWS plan (RDS + native S3) and need a pass to reflect Neon + Supabase.
